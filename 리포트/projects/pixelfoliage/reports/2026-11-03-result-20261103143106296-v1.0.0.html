작업 결과

현재 구현은 원본 잔디 시스템을 그대로 Unity에 이식한 상태가 아닙니다. 바람·접촉·단계별 시간 같은 개념을 다른 메시·셰이더로 구현하고 꽃·관목·나무용 구조를 더한 상태입니다. 원본의 외형을 만드는 일부 핵심 기능은 아직 빠져 있거나 단순화돼 있습니다. 원본과 같은 외형·더 낮은 GPU 비용을 달성했다고 검증한 상태가 아닙니다.

판정은 소스 기준입니다. ‘대응’도 같은 결과나 같은 성능을 뜻하지 않습니다. 최신 식생 개선은 컴파일·관리형 검사만 통과했으며 실제 화면 QA는 사용자 화면 조작 보류로 미실행입니다.

적용 내용

그래서 화면이 왜 다를 수 있나요?

차이는 밀도 숫자 하나가 아닙니다. 원본은 그림이 들어간 평면·카메라 전체 billboard·큰3색 영역·UV 가짜 원근·조명/구름 투영을 결합합니다. 현재 예제는 작은3D 잎·Y축 billboard·단순 색 변화·정점 휘어짐·자체 명암을 사용합니다. 이 방식 차이는 소스로 확인됐지만 각 요소가 최종 영상 차이에 기여하는 정도는 동일 조건의 분리 렌더로 아직 측정하지 않았습니다.

직전 개선에서는 잎의 폭·높이를 넓히고 대표 정원의 묶음을7000에서12000으로 늘렸습니다. 묶음당 정점은36개를 유지했지만 장면의 잔디 메시 총량은 증가합니다. 따라서 이 수정 자체를 전체 GPU 경량화로 설명하면 잘못입니다. 꽃·관목·나무 구조의 추가도 원본 잔디 표현을 재현했다는 근거는 아닙니다.

낮은 FPS가 줄여 주는 것은 무엇인가요?

  1. 시간 양자화: 움직임을 끊어 보이게 합니다. 현재 두 셰이더 모두 매 렌더에서 수식을 실행하므로 이것만으로 GPU 계산 생략을 주장할 수 없습니다.
  2. 위치 수집10Hz: 캐릭터 위치를 읽어 접촉 데이터를 갱신하는 CPU 작업의 횟수를 줄입니다. 현재 처리 클래스의600요청 모의 검사에서10Hz 수집100회·무제한600회를 확인했습니다. 전체 프레임 성능 측정은 아닙니다.
  3. 낮은 렌더 해상도: 원본의640×360과1920×1080은 픽셀 수가9배 다릅니다. 실제 속도가9배라는 뜻은 아닙니다. Unity Built-in의 사후 축소/재캡처를 이 원본 구조와 같은 최적화라고 부를 수 없습니다.

Pixel Camera와 무엇을 나누나요?

  • Pixel Camera: 저해상도 화면, 확대, 픽셀 격자, 색/윤곽 처리. 원본의 SubViewport/표시 역할과 연결됩니다.
  • Pixel Foliage: 풀/꽃/관목/나무의 배치·형상·바람·접촉·복원. 카메라를 꺼도 이 동작은 별도로 존재합니다.
  • Pixora: 이미지 작성/내보내기. 현재 식생 어댑터는 내보낸 Texture2D로 새 재질을 만드는 연결이며 실시간 문서 동기화가 아닙니다.

원본 재현을 목표로 할 경우의 우선순위

제안 순서는 원본 같은 스프라이트 카드 경로·3색 영역 → UV fake perspective와 billboard 정렬 → 광원/높이 투영 구름과 그림자 → 동일 조건 영상/성능 측정입니다. 아직 실행한 작업이 아니라 차이를 줄이기 위한 제안입니다. 기존 꽃·나무용 메시 경로와 선택할 수 있게 하는 구성이 적합하다는 판단입니다.
