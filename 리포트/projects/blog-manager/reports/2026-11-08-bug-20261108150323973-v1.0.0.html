예약 수정 기능 미적용 확인·실행 런타임 0.10.3 갱신

진행

작동하지 않는다는 보고 후 실제 설치·실행0.10.2와 새 편집 파일 누락을 확인했습니다. 브라우저를 조작하지 않고 런타임47파일과 서버를0.10.3으로 갱신했습니다.

접수→검토→진행→해결→종료
2026년 11월 9일 오전 12:03 KSTv1.0.0버그 추적

작업 결과

실제 설치 파일·실행 서버0.10.3, 런타임47파일 SHA일치·원고 파일 SHA불변·새 API HTTP400 거부 확인. 62검사 통과. 크롬 새 코드 활성화·실제 예약 수정은 미검증.

변경 내용

재현 조건

Windows · 설치 앱0.10.2에서0.10.3 런타임 갱신 · 현재 크롬 로드 버전 미확인

재현 순서

예약글 수정 기능 사용 불가 보고 → 설치 manifest/package·새 파일·실제health 대조 → 검증된 패키지47파일 백업/교체 → GUI 없는 Node 서버 재시작 → health/파일SHA/원고SHA/새API 대조

기대 동작

사용 중인 화면과 원고를 보존하면서 실제 실행 코드가 새 버전으로 적용되고 확장에서 예약 수정 저장이 동작

실제 동작

변경 전 소스0.10.3, 설치/실행/확장디스크0.10.2, reservation-editor.js없음. 변경 후 실행/확장디스크0.10.3·47파일해시일치·원고해시불변·새API잘못된입력HTTP400. 크롬 활성화는 아직 확인되지 않음.

원인

앞선 작업은 코드/설치본 생성·푸시까지만 수행하고 사용 중인 환경 보존을 위해 설치·크롬 반영을 보류했습니다. 실제 설치 폴더와 실행 서버가0.10.2로 남아 새 기능이 설치되지 않았습니다.

적용 내용

이미 검증된0.10.3 패키지의 런타임47파일을 백업하고 설치 경로에 적용했습니다. Node만 창 없이 재시작했습니다. 크롬·확장 관리·네이버 본문 수정/저장은 수행하지 않았습니다. 런처 EXE·설치 레지스트리를 포함한 전체 설치 실행과 구분합니다.

검증

실제health0.10.3·설치확장manifest0.10.3·런타임47파일 SHA일치·원고파일 SHA불변·서버 프로세스 MainWindowHandle0. 전체62검사 통과·건너뜀0. 새예약수정API에 존재하지않는ID를 전송해 검증된예약결과가 아니라는HTTP400응답 확인. 실제네이버저장성공을 뜻하지 않습니다. UI 전후캡처는 사용자화면조작금지에따라 미실행이며 화면검증통과로 기록하지 않았습니다.

남은 사항

크롬 확장 재로딩·실제 예약 원본 수정 저장 미검증. 사용 중인 브라우저와 네이버 원고는 변경하지 않았습니다. 확장 관리 화면 제어는 기존 도구 보안 정책 차단과 컴퓨터 유즈 금지 지시로 사용자 재로딩 응답 대기입니다. 원래 미완료 작업·이력은 보존합니다.

대화 요약(개별 시각 미기록): 사용자 “안되는데??” → AI 실행버전 대조 후 처리하겠다고 응답 → 설치0.10.2/새파일없음 확인 → 백그라운드47파일과서버갱신 → 사용자에게 기존확장새로고침1회 요청. 해당 요청은 기존확장관리화면 도구보안정책 차단과 컴퓨터유즈금지 지시 때문에 필요하며 권한확대나 새 설치 승인은 요청하지 않았습니다.

이전 보고의 “구현·격리 검증 완료, 실제 적용·네이버 수정 저장 검증 대기”는 당시 상태를 구분한 관찰이었습니다. 이번에 실제 런타임 적용까지 진행했지만 크롬 활성화와 원격 수정 검증까지 완료했다고 바꾸지 않습니다. 교훈 검토: 기존 전역의 구현·설치·실행 구분 원칙과 중복돼 전역지침 변경 없음. 현재 실행 앱은 사용자 기능 제공용으로 유지하며 새 GUI·탭·임시 서버는 만들지 않았습니다.
