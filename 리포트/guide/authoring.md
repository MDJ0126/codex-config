# Tracefolio 게시물 작성 가이드

작업 시작 전에 [작업 시작·반복 QA 메뉴얼](execution.html)을 읽고 [작업 메뉴얼](../manuals/index.html)을 등록·갱신합니다. 최초 필요한 작업은 최대30개, 이후에는1~5개씩 반복하며 전체 미완료 목록과 QA 이력을 보존합니다. [메뉴얼 JSON 템플릿](template-manual.json)을 사용합니다.

**작성 기준 v2 — 사람과 AI가 같은 폼·JSON·검사로 작성합니다.** 프로젝트별 결과 보고서와 버그 보고서를 같은 기준으로 관리합니다. 글마다 별도 HTML·CSS를 만들지 않습니다.

[보고서 작성 폼](../write/index.html) · [5단계와 공통 JSON 설명](workflow.html) · [결과 JSON 템플릿](template-result.json) · [버그 JSON 템플릿](template-bug.json) · [JSON 스키마](schema.json)

## 1. 분류와 단계

| 분류 | 세부 관리 |
| --- | --- |
| 프로젝트 | projects.json의 등록 ID와 로고 사용 |
| 결과 보고서 | 작업 결과·수정사항·검토·설정, 결과 상태, 우선순위 |
| 버그 보고서 | 접수 → 검토 → 진행 → 해결 → 종료, 심각도·우선순위·담당자 |

GitHub의 버그 이슈를 다시 열면 검토 단계로 돌아갑니다. 해결·종료에는 수정 내용과 검증 근거가 필요합니다. 과거 글도 원문 근거를 검토해 단계를 부여합니다. 수정·검증 근거가 있으면 해결, 미판정·중단·검증 대기는 검토, 수정 중인 범위가 남으면 진행으로 분류하며 완료 문구만으로 종료하지 않습니다. 원문·해시와 판단 근거는 별도 단계 검토 이력으로 보존합니다.

## 2. 사람이 작성하는 방법

사이트의 보고서 작성 폼에서 프로젝트·분류와 실제 내용을 입력합니다. 검사·미리보기는 공통 데이터와 Markdown을 보여줍니다. 공개 내용을 확인한 뒤 GitHub에서 최종 제출합니다. GitHub 로그인이 필요하고 등록 이후 자동 검사·배포를 거쳐 사이트에 표시됩니다. 브라우저 임시저장은 그 기기에만 남는 초안이며 사이트 등록이 아닙니다.

## 3. AI가 작성하는 방법

결과·버그 JSON 템플릿을 실제 값으로 채워 같은 검사 함수를 호출하는 CLI를 사용합니다. 원본 JSON을 보존하지 않고 Markdown을 직접 만들어 필수 항목을 우회하지 않습니다.

```sh
node 리포트/create-report.mjs --input report.json --dry-run
node 리포트/create-report.mjs --input report.json
node 리포트/build.mjs
node 리포트/verify.mjs
node 리포트/verify-migration.mjs
node 리포트/verify-editorial.mjs
node --test 리포트/tests/*.test.mjs
```

GitHub 접수를 사용할 때는 같은 JSON을 tracefolio:v2 표시와 json 코드 블록으로 등록합니다. 사이트 폼도 같은 내용을 만듭니다. 구체적인 표시와 이벤트 처리는 [공통 등록 설명](workflow.html)을 참고하세요.

## 4. 반드시 기록할 내용

| 항목 | 기준 |
| --- | --- |
| 제목·요약 | 실제 결과나 문제를 구체적으로 설명합니다. 요약은 180자 이내입니다. |
| 결과 | 끝난 일과 남은 일을 구분합니다. 구현·설치·실행·검증·배포를 하나의 완료로 묶지 않습니다. |
| 버그 재현 | 환경·버전, 재현 순서, 기대 동작, 실제 동작을 작성합니다. |
| 원인 | 검증한 원인만 씁니다. 확인하지 못했다면 미확인으로 남깁니다. |
| 변경 내용 | 실제로 바꾼 내용과 이유, 변경 전·후를 설명합니다. |
| 검증 | 실행한 대상·명령·결과와 범위를 기록합니다. 미실행·실패를 통과로 바꾸지 않습니다. |
| 남은 사항 | 미확인·제한과 다음 행동을 기록합니다. 기록이 없다고 남은 일이 없다는 뜻은 아닙니다. |
| 시간·검색 | 제안 시간, 실제 소요·완료 시각·시간대, XERJ 사용 근거를 기록합니다. 제공되지 않은 시간은 만들지 않습니다. |

## 5. 생성되는 게시물 형식

```text
프로젝트·보고서 분류·단계·우선순위
제목 / 요약 / 상태 / 날짜·버전
작업 결과
변경 내용 (버그: 재현 조건·순서·기대·실제·원인 포함)
검증
남은 사항
작업 시간
등록·상태 변경 이력
```

하나의 JSON 계약에서 format: tracefolio-v2 Markdown을 생성합니다. 빌드는 보존된 JSON을 재검사하고 Markdown이 같은 데이터에서 생성됐는지 확인합니다. 본문 H1 제목을 중복 작성하지 않습니다. 프로젝트별 최근 글을 참고하되 과거 v1·legacy 예외를 새 글 작성에 사용하지 않습니다.

## 6. 파일과 버전

```text
projects/<project>/posts/       생성된 Markdown
projects/<project>/reports/     생성된 HTML
projects/<project>/assets/      JSON·로고·첨부
projects/<project>/originals/   원문 백업
```

GitHub로 접수한 글은 TF-이슈번호로 표시됩니다. 수정 시 새 버전과 단계 이력을 보존하고 목록에는 최신 버전만 표시합니다. 오래된 기록·이전 버전·원문은 지우지 않습니다. 제품 버전과 문서 버전은 구별합니다.

## 7. 읽기와 공개 기준

- 한 문단에 하나의 결과나 근거를 쓰고 존댓말을 사용합니다.
- 표는 비교·매핑·검사 결과에 사용하고 긴 코드는 코드 블록에 넣습니다.
- 이미지에는 실제로 확인할 수 있는 내용을 설명하는 alt 문구를 씁니다.
- 첫 화면에 전체 로그·파일 목록·해시를 나열하지 않고 필요한 근거와 링크를 둡니다.
- raw HTML, script, iframe, 실행 URL을 사용하지 않습니다.
- 인증정보·개인 로그·세션 기록·비공개 데이터를 공개 등록하지 않습니다.
- 원문 시점의 테스트를 이번 작업의 검증으로 보고하지 않습니다.
- 푸시와 배포 성공을 구분하고 공개 URL까지 확인한 뒤 완료라고 안내합니다.

과거 v1·legacy 글은 읽기 호환을 유지합니다. 이 글들의 숫자와 판단은 원문 시점의 기록이며 현재 상태를 새로 증명하지 않습니다.

## 프로젝트 소항목

사이드바의 턴룸 아래 공통·통합 작업(turnroom), Pixora(pixora), Design Data Table(designdatatable)을 소항목으로 관리합니다. 상위 항목은 세 제품의 글을 합쳐 보여주며, 소항목은 해당 제품만 보여줍니다. 묶음 정의는 project-groups.json에서 관리합니다.

사람은 작성 폼의 턴룸 그룹에서 소항목을 고릅니다. AI는 기존 JSON project에 해당 소항목 ID를 기록합니다. 상위 묶음 ID인 products 또는 collection:products를 보고서 project로 쓰지 않습니다. 프로젝트별 폴더·원본·이전 링크는 유지합니다. 소항목에서 결과·버그 분류와 버그 5단계를 함께 필터링할 수 있습니다.

## 결과 이미지 필수 첨부와 압축

- 프로젝트 작업 결과를 보고할 때는 해당 프로젝트의 실제 실행 화면을 직접 캡처해 채팅과 HTML 보고서 양쪽에 첨부한다. 게임은 실제 게임 화면, 프로그램은 실제 프로그램 화면, 에디터·플러그인은 해당 에디터에서 작업 결과가 보이는 화면을 사용한다. 수정한 기능·상태·오류가 실제로 드러나는 장면을 고르고 무엇을 확인한 화면인지 설명한다. 이미지 첨부 의무를 채우기 위한 요약 카드·안내 도식·장식 이미지·가짜 화면·AI 생성 이미지를 만들어 대체하지 않는다. 지침·문서 수정 등 실제 실행 화면이 없는 작업은 이미지를 억지로 만들지 않고 그 사유와 확인한 변경 내용을 텍스트로 기록한다. 실제 화면 캡처가 필요한데 제한된 경우에는 캡처 미실행과 이유를 명시하고 화면 검증까지 완료했다고 보고하지 않는다.
- 보고용 이미지는 업로드 전에 불필요한 여백·중복 화면·메타데이터를 제거하고 필요한 해상도로 줄여 가독성을 유지하는 범위에서 최대한 압축한다. 래스터 이미지는 WebP를 우선 검토하고, 작은 글자·선·투명도가 손상되면 무손실 WebP·최적화 PNG 또는 SVG를 사용한다. 이미지당 200KB 이하를 우선 목표로 하되 글자 판독과 검증 근거 보존을 우선한다. 압축 전후 바이트·크기·실제 표시 품질을 확인하며, 원본은 필요 시 로컬에 보존하고 압축본만 첨부·게시한다.

이미지는 projects/<project>/assets/에 저장하고 JSON의 outcome·changes·verification 본문에서 `![확인한 내용](../assets/압축파일.webp)`로 첨부합니다. 사람의 작성 폼과 AI JSON 모두 같은 Markdown 이미지 문법을 사용합니다. 로컬 파일 경로를 공개 이미지 주소로 쓰지 않습니다. 채팅에도 실제 압축 이미지와 HTML 보고서 링크를 함께 제공합니다.


## QA 토론 · 개선 제안 · 새 기능 요청

보고서 상세의 **토론 시작**은 프로젝트와 원본 보고서를 자동 연결합니다. **QA 토론** 메뉴에서는 프로젝트·종류·논의 상태·검색으로 글을 찾고 원본 QA와 함께 다시 읽을 수 있습니다. 작성은 사이트 폼 또는 [토론 JSON 템플릿](template-discussion.json)과 같은 create-report.mjs --input 절차를 사용합니다. GitHub에서 최종 등록해야 공개 사이트에 반영되며 로그인 전의 미리보기·초안 저장은 등록이 아닙니다.

- kind: discussion, type: 토론. 결과·버그 수에는 섞지 않고 QA 토론 목록에 표시합니다.
- topic: qa(QA 토론), gap(부족한 점), proposal(개선 제안), feature(새 기능 요청).
- discussionState: open(논의 중), considering(검토 중), accepted(채택), deferred(보류), implemented(반영 완료).
- relatedReport: 같은 프로젝트의 실제 HTML 경로입니다. 예: projects/프로젝트ID/reports/파일.html. qa 종류에는 필수이며 다른 제안은 독립 글로도 작성할 수 있습니다.
- replyTo: 후속 글을 쓸 때 원본 토론의 HTML 경로를 기록합니다. 같은 프로젝트·같은 QA의 토론만 연결하며 순환 참조를 허용하지 않습니다.
- outcome에는 관찰 사실과 논의할 질문, verification에는 QA 근거·실제 화면, changes에는 제안·대안·기대 효과, decision에는 결정 이유·담당자·후속 작업, remaining에는 열린 질문을 기록합니다. 제안과 검증된 사실을 구분합니다.
- 채택·보류·반영 완료에는 decision이 필수이며, 반영 완료에는 verification도 필수입니다. 승인받지 않은 제안을 채택·구현 완료로 표시하지 않습니다.

토론의 H2는 **토론 내용 → QA 근거와 맥락 → 제안 및 대안 → 결정과 후속 작업 → 작업 시간**입니다. JSON 원본·Markdown·생성 HTML은 기존과 같이 프로젝트별 assets/submissions, posts, reports에 보존합니다. GitHub로 등록한 글의 수정 이력은 버전별로 보존하고 목록에는 같은 이슈의 최신 글만 표시합니다. **후속 글 쓰기**는 별도 글을 남겨 결론·보류 이유·새 제안의 맥락을 이어갑니다. GitHub 댓글은 토론 글의 외부 링크에서 볼 수 있으며 사이트에 자동 복제하지 않습니다.

## 작업 메뉴얼 형식

kind: manual은 결과·버그·토론과 별도 목록으로 관리합니다. 목표와 완료 기준 → 순차 작업 메뉴얼 → QA 반복 기록 → 남은 작업과 다음 반복 → 작업 시간 순서의 공통 H2를 사용합니다. 완료는 모든 작업의 결과·현재 버전 QA 통과와 전체 최종 QA가 필요합니다. 작업 메뉴얼의 상태는 버그 처리5단계와 구분합니다.

## 교훈 검토와 지침 반영

작업 종료 전 확인한 문제·재발 방지·사용자 정정을 검토하고 결과 보고에 **교훈 검토: 추가 / 통합 / 변경 없음**과 근거·적용 범위를 적습니다. 검증된 공통 행동 규칙은 전역 AGENTS.md에 반영하고 같은 의미의 항목은 통합합니다. 프로젝트·버전에 국한된 상세는 해당 프로젝트에 남기며 사용자 조건·예외·승인·검증 의무를 삭제하지 않습니다. [작업 메뉴얼의 교훈 반영 절차](execution.html)를 따릅니다.

최종 결과 보고는 반드시 중앙 저장소에 커밋·푸시하고 공개 배포된 개별 HTML·첨부의 외부 접근을 확인한 뒤 HTTPS 웹 링크로 제출합니다. 로컬 파일·file://·localhost 링크만으로 최종 보고를 끝내지 않습니다. 푸시·배포 실패는 보고서 공개 미완료로 구분합니다. [공개 보고 절차](execution.html)를 따릅니다.
