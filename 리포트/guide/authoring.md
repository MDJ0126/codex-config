# Tracefolio 게시물 작성 가이드

**작성 기준 v1 · 사람과 AI가 함께 사용하는 단일 기준입니다.** 새 글을 쓰기 전에 이 문서와 해당 프로젝트의 최근 보고서를 읽으세요. 사이트의 스타일은 공통 템플릿에서 관리하며 글마다 별도의 HTML·CSS를 만들지 않습니다.

## 1. 어떤 글을 작성하나요?

| 유형 | 사용하는 경우 | 본문에서 구분할 내용 |
| --- | --- | --- |
| 작업 결과 | 기능 구현·배포·설치 결과 | 완료한 범위와 남은 범위 |
| 버그 | 재현한 결함과 원인·수정·회귀 검증 | 재현 조건, 기대 동작, 실제 동작, 원인 |
| 수정사항 | 디자인·설정·문서·기존 기능의 변경 | 변경 전과 변경 후 |
| 검토 | 조사·비교·의사결정 자료 | 사실, 근거, 판단, 미확인 |
| 설정 | 환경·지침·도구 설정 | 실제 적용값과 확인 결과 |

서로 다른 프로젝트의 결과는 각각 작성합니다. 버그가 해결됐어도 유형은 버그로 유지하고 상태를 갱신한 새 버전을 추가합니다.

## 2. 파일 위치와 이름

```text
리포트/projects/<project>/posts/YYYY-MM-DD-주제-v1.0.0.md
리포트/projects/<project>/assets/주제-v1/이미지.png
리포트/projects/<project>/reports/같은이름.html  ← 빌드가 생성
```

project는 projects.json에 등록된 ID를 사용합니다. 예: pixora, codeassist, designdatatable, enginemigrator, windowsfoldersize, codex-config, affinity-cli. 새 프로젝트는 이름과 확인한 로고를 먼저 등록합니다. HTML 파일을 직접 편집하지 마세요. 이미 제출한 작업 내용을 수정할 때는 버전을 올린 새 Markdown을 작성합니다. 순수 편집 작업으로 기존 글을 정리할 때도 원문과 편집 전 백업을 보존합니다.

## 3. 필수 메타데이터

문서 첫 줄에 ---를 넣고 다음 항목을 **따옴표 없는 단일행 key: value**로 작성합니다. 다중행 YAML, 배열, 임의 HTML은 지원하지 않습니다.

```yaml
---
title: 선택 팝업의 키보드 이동 오류 수정
date: 2026-10-29T21:20:00+09:00
version: v1.0.0
status: 수정·회귀 검증 완료
state: complete
project: pixora
type: 버그
category: 에디터 UI
summary: 방향키 입력이 목록 밖으로 이동하던 문제를 수정하고 경계·선택·취소 동작을 검증했습니다.
format: tracefolio-v1
---
```

위 값은 작성 문법을 설명하는 예시입니다. 실제 버그나 테스트가 수행됐다는 뜻이 아닙니다. 복사 후 실제 작업의 값으로 모두 바꾸세요.

| 항목 | 규칙 |
| --- | --- |
| title | 결과나 문제를 구체적으로 표현합니다. 제품명이 프로젝트 표시와 중복되면 생략합니다. |
| date | ISO 8601과 시간대를 반드시 기록합니다. 한국 시각은 +09:00입니다. |
| version | 문서 버전입니다. 제품 버전과 구별합니다. 기존 글을 덮어쓰지 않습니다. |
| status | 현재 구현·실행·검증·배포 상태를 짧고 사실대로 씁니다. |
| state | complete, partial, progress, verification, blocked, archived 중 하나입니다. |
| project | 등록된 ID이며 폴더 이름과 같아야 합니다. |
| type | 작업 결과, 버그, 수정사항, 검토, 설정 중 하나입니다. |
| category | UI, QA, 빌드, 문서 등 세부 분야입니다. |
| summary | 180자 이내의 한두 문장으로 결과와 필요한 제한을 설명합니다. 경로·해시를 나열하지 않습니다. |
| format | 새 글은 반드시 tracefolio-v1을 사용합니다. legacy-v1은 승인된 과거 편집 기록에만 허용됩니다. |

## 4. 본문 순서

**본문에 H1 제목을 중복 작성하지 않습니다.** 화면의 제목은 title에서 자동 생성합니다. 다음 H2 제목을 같은 순서로 작성하세요. 하위 주제는 H3를 사용합니다.

### 작업 결과

첫 문장에 지금 끝난 일과 남은 일을 구분해 씁니다. 기능·설치·실행·검증·배포를 하나의 완료라는 말로 뭉뚱그리지 않습니다. 결과가 없으면 진행 중 또는 차단 상태와 실제 이유를 씁니다.

### 변경 내용

무엇을 왜 바꿨는지 구체적으로 씁니다. 수정사항은 변경 전·후를 설명합니다. 버그 유형에는 재현 조건, 기대 동작, 실제 동작, 원인을 반드시 포함합니다. 원인이 검증되지 않았으면 원인 미확인으로 씁니다. 별도의 검증 결과를 만들지 않습니다.

### 검증

실제로 실행한 명령·대상 버전·관찰 결과·증거 링크를 기록합니다. 성공 수치에는 분모와 범위를 붙이고 실패·미실행을 분리합니다. 소스 파일 확인, 테스트 대역, 실제 앱 실행, 원본과 대조는 서로 다른 증거입니다.

### 남은 사항

미확인·제한·다음 행동을 기록합니다. 남은 사항이 실제로 없을 때만 없다고 씁니다. 과거 보고서의 통과 기록을 이번 작업 검증으로 재사용하지 않습니다.

### 작업 시간

제안 시간:, 실제로 완료된 시간:, XERJ: 세 문구를 포함합니다. 시작 시 제시한 시간과 실제 소요·완료 시각·시간대를 구분합니다. 미완료 작업에는 완료 시각을 쓰지 않습니다. 코드 검색에 XERJ를 사용했는지와 대체 사유를 사실대로 기록합니다.

## 5. 읽기 좋은 글 작성

- 한 문단에 하나의 결과나 근거를 씁니다. 본문은 존댓말로 작성합니다.
- 전체 로그·파일 목록·긴 해시는 첫 화면에 나열하지 않습니다. 꼭 필요한 증거를 본문에 두고 나머지는 링크로 연결합니다.
- 표는 비교·매핑·테스트 결과에 사용합니다. 긴 코드는 언어를 지정한 코드 블록에 넣습니다.
- 실제 화면을 설명할 때만 이미지를 넣고 무엇을 확인할 수 있는지 alt 문구에 씁니다.
- 이미지 경로는 보통 ../assets/주제-v1/파일.png입니다. 링크와 파일명에는 공백 대신 하이픈을 권장합니다.
- raw HTML, iframe, script, style, 이벤트 속성, javascript: URL과 data: URL은 사용하지 않습니다.
- 인증정보, 개인 로그, 세션 기록과 비공개 데이터를 올리지 않습니다. 공개 사이트임을 기준으로 자료를 검토합니다.

## 6. AI의 제출 절차

1. 작성 가이드와 프로젝트 최근 글·실제 작업 증거를 읽습니다.
2. 결과 또는 버그 템플릿을 복사하고 메타데이터·본문을 실제 사실로 채웁니다.
3. 프로젝트 폴더에 저장하고 첨부파일을 같은 프로젝트 assets에 둡니다.
4. 아래 명령을 실행하고 실패가 있으면 고칩니다. legacy-v1로 바꿔 검사를 우회하지 않습니다.
5. 결과 화면·표·이미지·목차·좁은 화면을 확인합니다. 확인하지 못했으면 그 범위를 밝힙니다.
6. 승인된 범위에서 커밋·푸시합니다. Actions 성공과 공개 URL 응답을 확인한 뒤 배포 완료라고 보고합니다.
7. 채팅에는 핵심 결과와 공개 HTML 링크를 안내합니다. 글을 등록하지 않은 채 채팅만으로 보고를 끝내지 않습니다.

```sh
node 리포트/build.mjs
node 리포트/verify.mjs
node 리포트/verify-migration.mjs
node --test 리포트/tests/*.test.mjs
```

## 7. 과거 글을 읽을 때

legacy-v1 글은 이번 정리 이전에 작성된 자료입니다. 원문의 수치·미확인·실패·시점은 그대로 보존합니다. 과거 원문에 없는 원인·검증·시간을 채워 넣지 않습니다. 현재 상태를 보고하려면 새 tracefolio-v1 글을 작성하고 근거를 다시 확인하세요. 원문 백업은 originals, 편집 전 Markdown은 editorial-originals에 프로젝트별로 보관하며 웹 패키지에서는 제외합니다.
